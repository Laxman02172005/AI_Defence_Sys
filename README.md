# AI Defense Lab --- Red Team / Blue Team Payment Security

An end-to-end adversarial AI system for payment-security research that
**identifies emerging fraud scenarios, generates controlled synthetic
attack traces, detects them with a multi-stage AI defense pipeline, and
feeds observed misses back into adaptive evaluation and retraining**.

> **Competition:** Mastercard Innovation Challenge @ GFF 2026 --- AI
> Defense Lab for Payment Security\
> **Scope:** Controlled synthetic simulation only. This project does not
> connect to real payment systems or issue real payment requests.

## 1. What This Project Does

``` text
IDENTIFY
Emerging / novel payment-fraud attack patterns
        ↓
GENERATE
Research-grounded synthetic attack scenarios
        ↓
SIMULATE
Observable payment/security event traces
        ↓
DEFEND
Rule Filter → XGBoost → GCN → Autoencoder
        ↓
FUSE
Risk Fusion combines detector signals
        ↓
DECIDE
Decision Policy → ALLOW / REVIEW / BLOCK
        ↓
EXPLAIN
Feature importance + SHAP + case-level explanations
        ↓
ADAPT
Misses → Hard Examples → Stage-2 Retraining → Holdout Evaluation
        ↺
```

The key design principle is that **the attacks generated by the Red Team
become stress-testing and training material for the Blue Team**, while
the Blue Team's observed failures feed the adaptive loop.

## 4. Blue-Team Detection Pipeline

### Stage 1 --- Rule Filter

A deterministic first-pass layer catches obvious high-risk patterns
before expensive ML processing.

### Stage 2 --- XGBoost

A calibrated gradient-boosted classifier provides the primary tabular
fraud-risk score from engineered behavioral features.

### Stage 3 --- GCN

A graph-based detector captures relationship and network structure,
including suspicious connected entities and ring-like behavior.

### Stage 4 --- Autoencoder

An anomaly detector identifies behavior that differs from the learned
normal behavioral distribution.

### Stage 5 --- Risk Fusion

Signals from the detection stack are combined into a final risk score
rather than relying on a single detector.

### Stage 6 --- Decision Policy

The fused score is converted into an operational action:

``` text
ALLOW
REVIEW
BLOCK
```

Thresholds are stored with provenance describing the score source used
to derive them.

### Stage 7 --- Explainability

The system produces: - global feature importance - SHAP summary
visualization - case-level explanations - detector/fusion attribution -
decision-policy context

## 5. Adaptive Defense Loop

When the full cascade produces misses:

``` text
Miss
 ↓
Collect complete trace
 ↓
Generate candidate hard examples
 ↓
Validate candidates
 ↓
Keep ATO-validated examples
 ↓
Retrain Stage 2
 ↓
Evaluate on held-out data
 ↓
Check non-regression conditions
```

An important quality-control finding from the verified Problem 4
investigation is that the five retained ATO hard examples are **not five
independent attack patterns**. Their provenance traces back to two
source misses, and their model feature representations are highly
concentrated.

This is documented rather than hidden in:

`reports/problem4_ato_hard_example_diversity_investigation.md`

Therefore, the project does **not** claim that these five examples
represent five diverse attack families.

## 6. Verified Problem 4 Finding

The Round-1 → Round-2 ATO recall difference was investigated using the
repository's actual artifacts and evaluation logic.

``` text
Round 1 ATO recall: 98.97%
Round 2 ATO recall: 96.08%
```

The diagnosis found:

1.  None of the original 97 ATO cases flipped from correct to incorrect.
2.  The additional misses were newly introduced hard examples appearing
    in held-out folds.
3.  Adding five examples changes the `StratifiedKFold` partition because
    the dataset size changes.
4.  A controlled same-fold evaluation, where the five hard examples were
    used for training but excluded from the original 97-case test
    population, produced **0/97 misses**.
5.  The five hard examples are concentrated around two source misses and
    largely occupy the same feature template.

The detailed evidence is recorded in:

``` text
reports/problem4_ato_hard_example_diversity_investigation.md
reports/FINAL_VALIDATION_REPORT.md
```

The project therefore treats the original recall comparison as an
evaluation/measurement issue rather than claiming unsupported model
degradation.

## 8. Explainability

The explainability layer produces both global and case-level evidence.

Outputs include: - `global_feature_importance.json` -
`global_shap_summary.png` - `case_reports.json` - `case_reports.md`

Graph-specific attribution is treated carefully. A score increase is not
automatically described as a GCN effect unless the graph signal supports
that conclusion. Otherwise, the explanation attributes the increase to
fusion more generally.

## 15. Reproducibility and Provenance

The Red Team calibration layer separates:

-   **TIER_1_LEARNED** --- empirically learned from reference data.
-   **TIER_2_DERIVED** --- computed through explicit derivation rules.
-   **TIER_3_DOMAIN_MODELED** --- synthetic values based on documented
    domain assumptions where public telemetry is unavailable.

This prevents domain assumptions from being presented as empirical
facts.

## 16. Reference Data

The Red Team calibration layer uses public reference data including:

-   **PaySim (`paysim_v1`)** for transaction distributions and category
    mapping.
-   **IEEE-CIS Fraud Detection (`ieee_cis_fraud`)** for
    categorical/device-related distributions.

See `DATASET_LICENSE.md` and the project's provenance/registry
implementation for configuration.

Raw third-party datasets are intentionally excluded from version control
according to `.gitignore`.

## 17. Safety Boundary

This repository is a **controlled synthetic research environment**.

It: - generates synthetic entities and event traces - simulates
payment-fraud behavior - evaluates defensive models - does not interact
with real banking/payment systems - does not send real payment
requests - does not target real accounts or users

The goal is defensive testing and research.

## 20. Known Limitations

-   Synthetic realism is bounded by the public datasets available for
    calibration.
-   PaySim does not capture every real-world tail behavior or complex
    multi-currency geography.
-   IEEE-CIS device information is hashed/obfuscated.
-   Long-term behavioral relationships are domain-modeled where public
    longitudinal telemetry is unavailable.
-   The current ATO hard-example set is concentrated: five retained
    examples originate from two source misses and are highly similar in
    the Stage-2 feature space.
-   A small positive ATO evaluation population makes percentage recall
    sensitive to a small number of cases and to CV partition changes.
-   The verified artifacts represent a controlled simulation and should
    not be interpreted as production payment-system performance.
-   The deployed Streamlit prototype should use static/frozen verified
    artifacts or a separately hosted service rather than a local-only
    API.

These limitations are documented explicitly rather than hidden from the
reviewer.
